# 配置范围与优先级

ChronoDesk 的平台配置与项目设置是不同控制面。独立一级“系统设置”中的“公共配置”
和“邮件外发”调用 `/api/platform/*`，不得读取或修改当前项目的版本化配置快照。
项目成员、受理配置等 ProjectScope 控制能力只出现在“项目设置”导航分组；
日常知识搜索和沉淀属于“项目运营”，不因底层存在模型策略而藏进设置。“治理中心”
不承载公共配置、项目设置或日常业务页面。

配置约束的优先级为：

1. 平台 guardrail；
2. 公共模板和默认值；
3. 项目版本化 snapshot。

三个控制面的职责不得混用：

| 控制面 | 回答的问题 | 典型能力 |
|---|---|---|
| 系统设置 | 整个平台如何运行 | 公共默认值、邮件外发、安全策略、保留与清理 |
| 项目设置 | 当前项目如何受理和协作 | 基本信息、成员、请求类型、工作流、SLA、队列、路由、通知与外发边界 |
| 治理中心 | 谁在治理哪些跨项目资产 | 项目治理、平台身份与访问、审计与合规 |

“治理中心”不能容纳系统设置；“系统设置”也不能读取当前项目作为隐式作用域。
个人资料、账号安全、可信设备和登录历史属于用户自身账号控制面，只能从右上角头像
菜单进入，不占用侧栏一级导航。

项目只可在平台 guardrail 允许的范围内覆盖公共模板或默认值。项目设置中的版本化配置遵循草稿、
模拟、审批和不可变 release 语义；发布后的 snapshot 是项目运行时事实。

当前已实现的导航壳严格区分范围：`/system-settings` 与
`/system-settings/email` 使用平台级权限、文案和 scope 标识；“项目设置”只登记
已经存在且必须经过 `ProjectScope` 授权的能力。公共模板或默认值被项目采用时形成
版本化 snapshot，而不是运行时继续引用可变的公共记录。尚未实现的配置产品不会以
占位链接或伪公共配置 API 出现在导航中。

“通知与外发”页只解释项目消费哪些平台通道，以及到 Webhook/投递监控的
唯一管理入口；它不复制 SMTP 密钥或系统邮件配置。项目基本信息页展示不可变
Project Key、状态、说明和当前职责。归档项目只显示“当前版本暂不支持恢复”，
第一阶段不提供恢复操作。

知识库的 canonical 路径是 `/knowledge`。项目级默认 ACL、模型和发布规则只有在
形成独立、受保护且可审计的配置接口后，才可作为“项目设置”的策略页出现；不能复制
知识文章列表、搜索或编辑入口。“允许创建知识草稿”是项目成员关系上的独立能力，
因此由“项目设置 → 项目成员”管理；它不属于平台公共配置，也不会授予发布、ACL、
模型策略或索引管理权限。

现有 Ticket 继续绑定创建时采用的 Request Type、Workflow、SLA、路由、自动化、
审批和策略版本。公共默认后续变化不会让已有 Ticket 漂移到新 release。本文只
描述现有范围和优先级，不定义新的配置 API；新增配置能力必须先在领域服务和受保护
路由中实现，再登记导航入口。
